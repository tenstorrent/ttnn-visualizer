# Agent tools (MCP) — developer notes

User-facing documentation is [`docs/src/agent-tools.md`](../../../docs/src/agent-tools.md):
what the tools answer, what the numbers mean, and how to register the server with a
client. Read that first. The conventions this package holds to are in
[CONVENTIONS.md](../../../CONVENTIONS.md#agent-facing-tools). Tracked in
[#1995](https://github.com/tenstorrent/ttnn-visualizer/issues/1995).

This file covers only what a person changing the code needs.

## Layout

| Module | Holds |
|---|---|
| `handles.py` | Path → handle registry, and the inventory and capture facts `load_report` returns. No app database and no app context: `Instance` is a plain model of two paths, which is what lets the tools read the query classes directly. It does open the report's own SQLite file read-only, to report what the report can answer and how many devices it holds, and reads the cluster descriptor's `arch` block. |
| `tools.py` | The performance-report tools, `CANONICAL_PROJECTION`, and the caveat logic. `with_signposts` adds the signposts and the perf CSV's device count to `load_report`'s answer, read in one pass through `csv_queries.resolve_signposts`; a CSV that read cannot parse moves `handles.PERF_CSV_TOOLS` to unanswerable instead (`handles.without_performance_csv`). `program_cache` counts calls by `perf_flags.program_calls` and `perf_flags.repeat_cache_outcome`, the rule the `flags` group's recompute candidates read too. The two still differ by the flags' eligibility gate, as the view does: a repeat miss on a HOST-bound, signpost or missing row counts in `program_cache` and is never flagged. Its cache-disabled caveat is `perf_flags.CACHE_DISABLED_CAVEAT`, which the flags answer gives too. `zone_intervals` reads every zone once per handle through `DeviceLogProfilerQueries.query_every_zone_intervals`, and one zone a call through `query_zone_intervals` where that pass cannot hold the log or leaves the zone to be read alone. Both split each RISC's runs as its rows arrive, so they rely on tt-metal writing each RISC's markers in time order. |
| `report_diff.py` | What `diff_reports` calls a change (#2155): the thresholds and each summable metric's floor, unit and caveat, a capture's group totals, the median of a side's captures, which list each group goes to (`classify`), and how a group and the facts the captures differ in are named. Pure; `tools.diff_reports` reads the reports, keeps each capture's totals per range, by op code and, once a signature diff asks, by signature, which a repeat sums with its op codes since its report is dropped (`CacheVariant.DIFF_TOTALS`, which the registry keeps apart from the reports, up to `MAX_SCOPED_DIFF_TOTALS` ranges), keeps a report for the two compared captures only (`cached_report(keep=False)` for a repeat), keeps no totals read from a degraded report (`UnkeptSnapshot`), and refuses a capture given twice or a one-sided range. |
| `op_signatures.py` | An operation's tensor signature, from the performance CSV's `INPUT_n_*` and `OUTPUT_n_*` columns, for `diff_reports`' `match: signature` (#2155). Read apart from the generated report and only when asked, so no other tool's snapshot grows. It numbers rows as tt-perf-report's pandas read does, skipping an empty or whitespace-only line, since `diff_reports` finds a row's signature by the CSV position its report id names; the generator's own pass-through columns count such a line, which only a hand-edited CSV holds. |
| `hw_utilisation.py` | `hw_utilisation` (#2371): tt-metal's hardware counters per unit over the whole report, weighted by device time, and operations ranked by any counter label. It reads every counter's average, minimum and maximum columns and the full-grid ones once per capture (`tools.hardware_counter_table`, `CacheVariant.HARDWARE_COUNTERS`) by CSV position, as the generator's `csv.DictReader` numbers rows, beside the canonical report for device time. Header discovery, the vendored label-to-family map, each label's capture groups, which groups a capture filled and why a label is missing (`absence_hint`) are `ttnn_visualizer/hardware_counters.py`'s, shared with the generator, which copies the headline averages into the app's rows only when the CSV has counter columns (and their minimum and maximum only with `detail_columns`), and with `/api/performance/counters/<perf_id>`. The `counters` include group reads those row keys. The architecture it names is `ttnn_visualizer/device_architecture.py`'s port of `stringToArchitecture` and `DeviceArchitecture`, which `perf_flags` reads too, so the counters and the flags spell it alike; it and the route read it through `DeviceLogProfilerQueries.architecture`. |
| `stall_breakdown.py` | `stall_breakdown` (#2372): each compute thread's issue and stall rates and named waits, from the same counter table `hw_utilisation` reads, beside the CB waits tt-metal's sum zones time, per op, ranked by an average core's stalled time. The per-op figures are `ttnn_visualizer/pipeline_stalls.py`'s, which `/api/performance/counters/<perf_id>` answers with too, so the tool and the operation's Stalls tab read one rule: which labels belong to which thread, the CB sums divided by the CSV's `CORE COUNT` (`core_count`, a detail column, since tt-perf-report's `cores` counts a DRAM-sharded matmul's DRAM-interface workers and the route has only the CSV row), the CB columns ignored on an op without a compute kernel (`cb_waits_ignored`, which the `riscs` include group does not apply yet: #2376), the largest of the stall rates and CB shares as the op's stalled share, and each part's state with its fill hint, as a counter's absence gives one. Both read an op's counters through `hardware_counters`' one reader, `CounterTable.reader` here and in `hw_utilisation`, `CounterHeader.row_reader` in the route, and the tool finds a row's table position with `tools.csv_position`. The tool hands it the raw cells through the report's detail columns, keyed back to their CSV names, and picks rows with `tools.perf_rows`, as `core_spread` names one, and `tools.costliest_rows`. An op code's calls are ranked on `pipeline_stalls.stalled_us`, the stall rates and CB sums alone, before the ones returned are read in full. Whether a capture had sum profiling is whether any compute op in its CSV, on any device's row, carries a CB wait, and one reader decides it for both: `OpsPerformanceReportQueries.read_sum_profiled`, which reads the CSV once per file. The route asks it through `sum_profiled_or_false_if_unreadable`, only for a compute op without one, and counts a CSV it can't read as without it; the tool asks it through `tools.sum_profiled`, which keeps the answer once per capture (`CacheVariant.SUM_PROFILING`, under `_per_capture`'s same-source check) and lets a failed read fail the call rather than keep it. |
| `perf_detail.py` | The field groups `include` adds to a performance row (#2153), and what fills a field no row carries. The generated rows hold the raw CSV columns behind them only because `tools` asks for `detail_columns`; the app's rows do not (#2159). |
| `operations.py` | The memory report database tools, including provenance (arguments and call site) and per-operation L1 pressure (`_compute_l1_pressure`, a port of `computeL1PressureForOperation` in `src/functions/l1Pressure.ts`, held to it by the `l1PressureParity` golden; `pnpm run agent:parity-golden` regenerates it, and a change on either side fails one test or the other). `scoped_devices` keeps one row per device id as `fetchDevices` does, which the golden does not reach, so `test_agent_operations.py` holds it. Opens its own read-only connection: `LocalQueryRunner` reads `Instance.profiler_path` as the SQLite file, while a handle holds the directory the caller named. |
| `linking.py` | The join from a performance row to the memory report operation that launched it: a port of the app's positional match (`src/functions/deviceOperationMatching.ts`). `TestMatcherParity` restates the app's cases, so it catches drift in the port only: **a change to the app's matcher or the order lists in `useAPI.tsx` fails nothing here and must be mirrored in `linking.py` by hand** (`isDeviceOperation` and the scope pairing are in `scope_outcomes.py`, below) — as must a change to `isCountableDeviceTime`, or to `enrichRowData`'s `parseFloat` of the cell, which `tools.countable_device_time` restates (reading the cell through `tools.metric_number`, `js_values.js_parse_float` for device time) for every device-time share and costliest-first ranking, `operation_detail`'s among them; `top_ops`, `project_row`, `op_breakdown` and `diff_reports` read every metric through `metric_number`, which reads each text column as `enrichRowData` does (through `row_cells`, #2440), so a row reports, ranks and sums the number the app shows. ## Running it from a source checkout

```bash
uv run ttnn-visualizer-mcp
```

Drive it by hand with a here-doc, which is faster than attaching a client while iterating:

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"load_report","arguments":{"performance_path":"/path/to/report"}}}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"zone_timings","arguments":{"handle":"report-1","limit":5}}}' \
  '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"core_spread","arguments":{"handle":"report-1","limit":3}}}' \
  '{"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"zone_intervals","arguments":{"handle":"report-1","zone":"BRISC-KERNEL","limit":3}}}' \
  | uv run ttnn-visualizer-mcp
```

`BRISC-KERNEL` is in every capture, but a kernel zone starts once per run, so that call
answers with no intervals and a caveat; name a zone `zone_timings` lists that recurs within
a run, such as a loop's, to see intervals.

The database tools take a memory report directory instead, and a report with both is loaded in
one call:

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"load_report","arguments":{"memory_report_path":"/path/to/memory/report"}}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"memory_profile","arguments":{"handle":"report-1","buffer_type":"L1","limit":5}}}' \
  | uv run ttnn-visualizer-mcp
```

## Three things to know before editing

**`stdout` is protocol.** Logs go to stderr, and `tools._generate_canonical_report`
captures `tt_perf_report`'s own printing — it prints progress and temp paths, which would
land mid-frame and corrupt the stream. The usage exporter runs `curl` in the same
process when aggregate collection is opted in, and `usage_metrics._post_with_curl`
captures its output for the same reason; `test_mcp_stdout_is_only_protocol_while_exporting`
guards it.

**Report cells are strings.** `device_time` arrives as `"16.478"` and `cores` as `"110"`,
so nothing numeric is compared directly. A text metric, or the detail field beside one,
goes through `row_cells.cell_number`, which reads it as `enrichRowData` does; any other
goes through `cells.finite_number`. Both drop a NaN or an infinity, which would reach the
client as invalid JSON.

**The call-site parse has a second implementation.** `parse_frames` must agree with
`parseStackTraceFrames` in `src/functions/stackTraceSource.ts`, which finds the frames the
operation details panel links (those whose file the report holds) and frame 0, the call
site, that its Source button opens —
two answers to "where is this op from" that disagreed would be worse than one. Both match
one anchored pattern per line, so a frame's file and line always come from the same line,
and a path with a quote in it is no frame on either side. The frontend splits lines on
CRLF, CR and LF, where `splitlines()` also splits on a few rarer separators (U+2028, U+2029,
form feed, VT, NEL, U+001C to U+001E). Which side reads such a line depends on where the
separator falls. After the line number, the frame is read only here, since `splitlines()`
leaves the frame whole and JavaScript's `.` stops at it. Inside the quoted path, it is read
only in the app, since JavaScript's `[^"]*` takes it and `splitlines()` cuts the frame in
two. CPython writes file names as they are, so a file named that way does reach a trace.
Separately, `parse_frames`' `\d` matches any Unicode digit, where JavaScript's matches only
ASCII, so a line number in, say, Arabic-Indic digits is a frame only here; CPython never
writes one. `TestFrameParity` transcribes the frontend pattern, pins that both read the
same frames, and pins these differences.

The frontend has a second input, `stack_trace_source_file_id`, with no equivalent here.
It is one id per trace, for frame 0's file (tt-metal's writer stores the first file a trace
names), so only frame 0 sends it.

**Two size units share one response.** `buffers.max_size_per_bank` is per bank and
`tensors.size` is a whole-tensor byte count, so `operations.py` labels both rather than
letting the field names imply they are comparable. The HTTP serializers re-expose the
per-bank column as plain `size` (`serializers.py:309`), which is how easy the misreading
is.

**Adding a tool means adding it to `_tool_table`**, with a `title` and a description carrying
the caveats an agent needs *before* choosing it — not only in the response. A rule every tool
shares goes in `INSTRUCTIONS` instead, which clients put in the system prompt; keep it short.
It also means a row in the
tool table of [`docs/src/agent-tools.md`](../../../docs/src/agent-tools.md), in the same
change: that page is the only description of this surface a client's reader gets, and #2035
puts it inside the application, so a tool missing from it goes missing for the user too.

## Swapping in the official SDK

The transport is hand-rolled to keep a resolver tree and a licence scan off a spike. The
replacement is contained to `server.py`: add `mcp` as an optional dependency, and re-express
`_tool_table` as SDK tool registrations. The tools themselves take a registry and plain
arguments, so they do not change.
